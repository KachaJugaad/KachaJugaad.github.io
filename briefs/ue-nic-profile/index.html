Proposal · AI cluster operations · UE Spec 1.1, Ch. 7Proposal, not a product

UEC 1.1 points NIC management at a profile nobody has published

1What can't an operator see today?

A link had trouble, but where: cable, NIC receiver, or switch transmitter? The NIC's receive-side counters know. No published Redfish profile I could find asks the BMC for them.

2What changed on 12 October 2026?

UE Specification 1.1 came out. It says NIC management "shall" extend the OCP NIC profile into a UE NIC profile. I could not find that profile published.

3What would close the gap? Proposal

Publish the UE NIC profile: the OCP NIC profile plus LLR, CBFC and FEC counters, checked with the open-source Redfish Interop Validator.

CBFC = sender needs buffer credits before sending. FEC = error correction built into the link.

4Who gains, and how?

  • Operators: find the faulty part, not just the link.
  • NIC and BMC vendors: one target instead of OEM fields.
  • Tool builders: one parser for every vendor.

CSIG = packet tag recording worst congestion on path.

5Where does this come from?

  • initial focus: link layer and PHY. §7.1, p752
  • UE NIC endpoint manageability shall be prescribed by extending the OCP Ethernet NIC profile. §7.4, p756
  • Table 7-1: 16 tasks, all Mandatory; none for LLR, CBFC or CSIG. p756
  • Switch: Port LLR profile; CBFC virtual channel, credit profile, credit pool; CSIG. §7.6, p759–760
  • OCP NIC profile v1.0.0, PortMetrics: RX/TX bytes and errors.
  • OCP neocloud workstream lists NIC and fabric counters as a gap.

6What will people object to?

"Just run ethtool on the host."I think in bare-metal GPU clouds the tenant owns the OS; operators cannot install agents. The BMC path is the operator's, and works with the OS down (p755).
"The switch already counts its replays."It knows it resent frames, not which part failed.
"Vendors expose this in OEM fields."OEM fields differ by vendor, so every fleet tool needs special cases. I have not checked specific vendors.
